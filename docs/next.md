## 0-1. 번호가 갈렸다는 사실을 훑기 화면은 말하지 않는다

번호는 두 군데서 읽힌다 — zxing이 막대를 읽은 값과, 모델이 사진에 인쇄된 숫자를 눈으로
읽은 값. **이제 어느 화면에서든 막대 쪽이 기본이다.** 막대는 검산 자리가 있어 틀리면
아예 값을 안 내놓고, 인쇄된 숫자를 읽는 눈에는 그런 장치가 없다.

직접 올리는 화면은 갈렸을 때 "사진과 맞는지 확인해주세요"라고 짚어준다. 갤러리 훑기는
그 자리가 없다 — 카드가 그대로 등록까지 간다.

- [ ] 갈린 사실을 훑기 카드에도 보여줄 것. 막대가 틀렸을 때(검산 없는 규격이면 가능하다)
      사람이 알아챌 자리가 지금은 없다. 번호가 틀리면 매장에서 못 쓴다.
- [ ] 등록된 것들 중에 번호가 틀린 게 있는지 한 번 훑어볼 것. 이 결정을 하기 전에
      등록된 건들은 모델이 읽은 숫자로 들어갔을 수 있다.
- [ ] `client/src/components/BarcodeModal.jsx:73`은 저장된 숫자로 막대를 **새로 그린다**.
      원본에서 잘라둔 바코드 이미지(`barcode_image_path`)가 있는데도 쓰지 않는다. 숫자가
      틀리면 그려진 막대도 틀린다. 크롭을 대신 보여주는 쪽이 나은지 재볼 것 — 사진으로
      찍힌 막대라 스캐너가 못 읽을 수도 있어서, 지금 방식에도 이유는 있다.

## 0. 상품명을 한 글자씩 다르게 읽는다

"떠먹는 스트로베리"가 **"더먹는"**으로 나온다. 태수님이 마지막에 잡기로 한 항목이다.

### 지금까지 한 것

압축이 원인인 줄 알았다. 모델이 보던 사진이 보관용으로 눌러둔 사본(1400px, 품질 0.82)
이었고, 한글은 획 하나로 갈리니(떠/따, 반/밤) 압축 자국이 그 위에 앉으면 다른 글자가
된다고 봤다. 실제로 같은 사진이 부를 때마다 "따먹는"과 "뚜렛는"으로 갈렸다.

모델용 사본을 따로 떴다 — 1568px, 품질 0.95 (`client/src/utils/imageAnalyze.js`).
이미지 토큰은 픽셀 수로만 매겨져서 화질을 올려도 요금은 그대로다.

**절반은 맞았다.** "황금올리브 반반"이 제대로 나오게 됐고, 못 읽는 건이 없어졌고,
무엇보다 **여러 번 읽혀도 매번 같은 답**이 나온다. 흔들리던 것이 멎었다.

### 남은 것은 다른 문제다

답이 일정해졌다는 건 이제 노이즈가 아니라는 뜻이다. 모델이 이 해상도에서 그 글자를
진짜로 "더"로 본다. 화질을 더 올려도 같은 답이 나올 것이다.

여기서 쓸 수 있는 수는 두 가지뿐이다.

- [ ] **상품명 자리만 잘라서 크게 보내기.** 지금은 세로로 긴 캡처를 통째로 보내는데,
      화소 상한(115만) 때문에 폭이 700픽셀 언저리로 묶인다. 글자가 있는 부분만 잘라
      보내면 같은 화소로 몇 배 크게 볼 수 있다. 자를 위치를 알아야 하는데, 모델이 이미
      `thumbnail`로 상품 그림 위치를 짚고 있으니 같은 방식으로 상품명 위치도 짚게 하고
      두 번 부르는 식이 된다. 호출이 두 배가 된다.
- [ ] **모델을 올리기.** `claude-haiku-4-5` → `claude-sonnet-5`. 한글 판독은 확실히
      나아지지만 값이 3배다($1/$5 → $3/$15). 한 건 6원이 18원이 된다.

먼저 재볼 것: **같은 사진을 Sonnet에게 한 번 보내보고** 실제로 "떠먹는"이 나오는지.
안 나오면 모델을 올려도 소용없으니 자르는 쪽으로 간다. 두 번 부르는 값(12원)과 모델을
올리는 값(18원)을 비교하는 건 그다음이다.

관련: [scan-cost.md](scan-cost.md)

## 1. ~~지도와 외부 연동이 앱에서 안 된다~~ — 됐다

앱은 화면을 **`https://localhost`** 에서 연다. Capacitor의 기본값이고
(`hostname = "localhost"`, `androidScheme = https`), `app/capacitor.config.ts`에
따로 지정한 것이 없어 그대로다. 개발자센터에는 `https://ceaser501.github.io`만
등록돼 있어서 SDK가 401로 떨어졌다.

**등록하는 자리를 찾는 데 가장 오래 걸렸다.** 카카오 콘솔에는 도메인을 적는 칸이
여럿이고 쓰임이 다르다. 다음에 또 헤매지 않도록 적어둔다.

| 자리 | 무엇에 쓰나 |
| --- | --- |
| **앱 → 플랫폼 → Web → 사이트 도메인** | **JavaScript SDK가 보는 유일한 칸** |
| 앱 → 제품 링크 관리 → 웹 도메인 | 카카오톡 링크 공유 미리보기 |
| 앱 → 일반 → 앱 대표 도메인 | 같은 계열. SDK와 무관 |
| 제품 설정 → 카카오 로그인 → Redirect URI | 로그인 후 돌아올 주소 |

- [x] 카카오 **플랫폼 → Web → 사이트 도메인**에 `https://localhost` 추가 → 지도가 뜬다
- [x] 실패 이유를 화면에 남긴다 — `client/src/utils/kakaoMap.js`가 이유를 같이
      돌려주고 `client/src/components/StoreDetailSheet.jsx`가 그대로 보여준다.
      앱에서는 CapacitorHttp로 한 번 더 불러 상태 코드와 본문까지 적는다.
      401을 눈으로 본 덕에 "네트워크냐 도메인이냐"를 한 번에 갈랐다.
- [x] **T맵 길안내** — `intent://` 형태를 풀어주는 것은 크롬이지 웹뷰가 아니다.
      Capacitor는 자기 도메인 밖의 주소를 만나면 `new Intent(ACTION_VIEW, url)`로
      그대로 넘기는데(`Bridge.launchIntent`), 그 url의 scheme이 `intent`라서 받아줄
      앱이 없다. 던져진 `ActivityNotFoundException`은 아무도 잡지 않는다(소스에
      `// TODO`로 남아 있다). 앱 안에서는 `tmap://`를 그대로 넘기고, 대체 주소를
      실을 수 없으니 "1.5초 뒤에도 화면이 그대로면 스토어로"를 같이 쓴다.
- [ ] **아직 안 본 것** — 경로 그리기(자동차·도보)와 주변 매장 검색
      (`supabase/functions/search-places`). 후자는 서버가 부르는 REST라 도메인
      제한과 무관하지만, 지도가 죽어 있어서 확인할 기회가 없었다.

## 2. 여러 장을 한 번에 등록하기

지금 `+`는 한 건씩만 받는다. 여러 장을 받아 바코드 번호가 같은 것끼리 묶고,
읽어낸 값을 확인시킨 뒤 한꺼번에 넣는다.

시안 네 가지를 그려뒀다 — <https://claude.ai/code/artifact/696cb219-748e-4d78-b610-58383057bbcb>

| | 전부 잘 읽힌 날 | 한 건 흐릴 때 | 기존 화면과 |
| --- | --- | --- | --- |
| A 묶음 띠 + 편집판 | 5번 눌러야 | 그 건만 고치면 끝 | 새 화면 |
| **B 카드 목록** | **1번** | 그 카드만 펼침 | **같음** |
| C 한 장씩 넘기기 | 5번 넘김 | 넘기다 만남 | 새 화면 |
| **D 빠진 것만 묻기** | **1번** | 그 칸만 물음 | **같음** |

**추천은 B를 뼈대로, 카드를 펼치면 A의 편집판, 등록 직전에 D의 질문이다.**
셋은 배타적이지 않다.

### 왜 B인가

- 전부 잘 읽힌 날에 손이 **한 번만** 간다. 카카오톡 원본은 거의 다 제대로 읽히니
  그게 대부분의 날이고, 그 경우를 빠르게 만드는 것이 여러 장을 한 번에 올리는 이유다.
- **아이폰에서는 이 화면이 유일한 다건 경로다.** 사진첩을 훑을 수 없기 때문이다
  (`client/src/utils/gallery.js`의 `isGalleryScanSupported` 참고). B로 가면
  안드로이드의 자동 찾기 결과와 아이폰의 직접 올리기가 똑같이 생긴 화면으로 모인다.
  배울 것도 만들 것도 하나가 된다.

### 이미 있는 것

묶는 규칙은 새로 만들 것이 없다. `client/src/utils/gallery.js`에 그대로 있다.

- 같은 바코드 번호면 한 건 (`seenCodes`)
- 원본(카카오톡·다운로드)이 있으면 캡처는 빼고 (`isOriginal`)
- 바코드가 사진 폭의 25%에 못 미치면 후보에서 제외 (`MIN_BARCODE_COVERAGE`)

### 할 일

- [x] 시안 확정 — B를 뼈대로, 카드를 펼치면 편집판, 빠진 칸만 묻기
- [x] `+`에서 사진 여러 장 받기 — 이미 여러 장을 받고 있었다. 달라진 것은 그 사진들이
      서로 다른 기프티콘일 때다. 예전에는 "다른 기프티콘인데 새로 시작할까요?"라고
      물었는데, 다섯 장을 골라 온 사람에게는 네 번 묻고 네 번 버리는 셈이었다.
- [x] 받은 사진을 위 규칙으로 묶기 — `collect()`에서 사진 한 장을 가져오는 걸음만
      밖으로 뺐다(`read`). 사진첩은 네이티브에게 묻고 직접 고른 사진은 브라우저에서
      줄인다. 묶고 고르는 판단은 한 벌 그대로다.
- [x] 묶은 결과를 확인시키는 화면 — 훑기 화면을 그대로 쓴다(`files` prop). 새 화면을
      만들지 않았다. 아이폰에서는 이 길이 유일한 다건 경로가 되므로, 둘이 다르게
      생기면 배울 것도 고칠 것도 두 벌이 된다.
- [x] 일괄 등록 — `registerAll`과 미리 올려두기를 그대로 쓴다
- [x] 카드를 펼쳐 빠진 칸 채우기 + 읽다가 막힌 건 다시 읽기

### 아직 안 한 것

- [ ] **아이폰에서 실제로 되는지.** 로직은 브라우저에서 도는 것뿐이라 될 것으로 보지만,
      아이폰 빌드 자체가 아직 없어서 확인할 방법이 없다.
- [ ] **한 번에 몇 장까지 받을지 정하기.** 지금은 상한이 없다. 사진첩 훑기는 200장으로
      묶어뒀는데(`MAX_IMAGES`), 이쪽은 사람이 손으로 고르는 것이라 그렇게 많이 고를 일이
      없다고 보고 두었다. 서른 장쯤 골랐을 때 어떻게 되는지는 재보지 않았다.
- [ ] **묶기를 두 번 돈다.** 등록 창이 "몇 건인가"를 보려고 얕게 한 번 읽고, 넘겨받은
      화면이 정밀하게 다시 읽는다. 두 장이면 눈에 안 띄지만 열 장이면 티가 날 수 있다.
      한 번 읽은 결과를 넘기는 쪽이 맞는데, 두 화면이 필요로 하는 모양이 달라서 미뤘다.

## 4. 앱을 열었을 때 맨 위에 무엇을 띄울까

자리는 하나인데 띄우고 싶은 것이 셋이었다 — 환영 인사, 운영 공지, 주변 매장 안내.
겹치면 목록이 두세 줄씩 밀린다.

**정한 것: 그 자리는 주변 매장 안내가 갖는다.** 기프티콘을 못 쓰고 버리는 진짜 이유는
기한을 몰라서가 아니라 매장 앞을 지나가면서도 가진 걸 떠올리지 못해서라, 이 앱에서
가장 힘이 센 자리다. 나머지 둘은 다른 길을 찾는다.

### 4-1. 환영 인사 — 공지 시스템에 얹지 않는다

지금은 운영 공지로 띄우고 있는데, 공지는 성격이 "닫을 때까지 남는 것"이다
(`client/src/components/NoticeBanner.jsx`). 거기에 "처음 한 번만"을 섞으면 공지 규칙이
거짓말이 된다.

- [ ] 가입하고 처음 들어왔을 때만 그 자리에 뜨는 별도의 띠
- [ ] X로 닫거나, 앱을 껐다 켜면 다시 안 뜬다
- [ ] 기존 환영 공지는 지우지 않고 그대로 둔다

### 4-2. 운영 공지 — 종 안으로

서버 점검이나 장애는 반드시 알려야 하는데, 맨 위 띠는 눈에 잘 안 띄고 주변 안내와
자리를 다툰다. 종 옆에 아이콘을 하나 더 두는 것도 생각했지만 헤더가 빽빽해진다.

**푸시는 쓰지 않는다.** 한 번 그렇게 하려다 접었다. 공지를 종류별로 늘어놓아 보니
미리 알려야 하는 것이 거의 없었다 — 새벽 점검은 그 시간에 다들 자고, 장애는 미리 알 수
없고, 기능 안내는 애초에 푸시할 일이 아니다. 전부 앱을 열었을 때 알면 되는 것들이다.

그런데 이런 것으로 푸시가 몇 번 가면 정작 **기한 임박 푸시까지 같이 꺼진다.** 이 앱에서
푸시는 기한 임박 하나로 아껴 쓴다.

대신 층을 둘로 나눈다. `supabase/schema.sql:910`에 `is_important`가 이미 있으니 그걸 쓴다.

| | 어디로 | 얼마나 |
| --- | --- | --- |
| 보통 공지 | 종 안에 쌓임 (배지) | 늘 |
| 중요 공지 (`is_important`) | 앱 열 때 작은 팝업 한 번 | 아주 드물게 |

팝업은 거슬린다. 그래도 "반드시 봐야 하는 것"을 채우는 방법이 이것뿐이고, 드물게만 쓰면
거슬림이 값을 넘지 않는다. 무엇보다 **맨 위 띠 자리를 안 쓴다** — 주변 매장의 자리를
그대로 지킬 수 있다.

- [ ] **보통 공지는 종 안에 합류.** 아이콘을 늘리지 않고 이미 있는 배지를 쓴다.
      목록에서는 확성기 아이콘과 배경색으로 가족 활동과 구분한다.
- [ ] **중요 공지는 앱 열 때 팝업 한 번.** 닫으면 그 공지는 다시 안 뜬다.
- [ ] 데이터가 다르다는 것에 주의 — 종에 쌓이는 것은 `activities`(가족 단위)이고 공지는
      전체 대상이다. 한 테이블에 섞지 말고 화면에서 합쳐 보여준다.
- [ ] 맨 위 띠에서 공지를 뺀다. `NearbyBanner`의 `yielded`도 함께 걷어낸다 —
      비켜설 상대가 없어진다.

| 언제 찾나 | **앱을 열고 목록이 처음 채워졌을 때 딱 한 번** (`ranRef`) |
| 켠 채로 이동하면 | **아무 일도 안 일어난다.** 다시 안 찾는다 |
| X로 닫으면 | `sessionStorage`라 **앱을 껐다 켜면 다시 뜬다** |

캐시에 10분·300m 규칙이 있지만(`CACHE_TTL_MS`, `CACHE_MOVE_M`), 다시 찾지를 않으니
그 규칙이 쓰일 일이 앱을 껐다 켤 때뿐이다.

- [ ] **앱이 다시 앞으로 올 때 한 번 더 찾는다.** `@capacitor/app`의 `appStateChange`를
      쓰면 된다(이미 깔려 있다).

      홈 버튼으로 뒤로 보냈다 다시 열 때, 화면을 껐다 켤 때, 다른 앱 쓰다 돌아올 때가
      여기 든다. 앱을 아주 꺼버렸다 켜는 경우는 지금도 새로 찾는다 — 컴포넌트가 새로
      뜨기 때문이다. 문제는 **사람들이 앱을 잘 안 끈다**는 것이다. 홈을 누르고 주머니에
      넣는다. 그러고 500m를 걸어가서 앱을 다시 봐도 아까 그 내용이 그대로 있다.

      캐시(10분·300m)가 이미 있어 호출은 안 샌다. 켜둔 채로 주기적으로 도는 것은 하지
      않는다 — 배터리와 검색 한도를 쓰는데, 앱을 켜둔 채 걷는 일은 드물다.
- [ ] **X를 누르면 그날 하루 안 뜬다.** 움직였어도 그날은 안 띄운다.

      한때 "300m 넘게 움직였으면 내용이 달라졌으니 다시 띄우자"고 했다가 접었다.
      그건 앱 입장의 논리다. 겨우 한 줄짜리 띠에 X를 눌렀다는 건 안 보겠다는 뜻이고,
      거기서 앱이 이기려 들면 안 된다. 다음 날 다시 띄우는 것으로 충분하다.
      날짜 하나만 기억하면 되니 만들기도 더 단순하다.
