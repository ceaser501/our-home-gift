# 스토어 출시 대응 계획

Play 스토어와 App Store에 **공개 배포**한다는 전제로, 지금 구조에서 바꿔야 할 것과
새로 해야 할 것을 정리한 문서다.

보안 쪽 점검과 조치는 [docs/security.md](security.md)에 따로 있다. 이 문서는 **심사 통과**와
**플랫폼 정책**에 초점을 맞춘다. 두 문서의 체크리스트를 모두 비워야 제출할 수 있다.

- 정리 시점: 2026-08-12
- 배포 방식이 "지인에게 APK 링크"에서 "스토어 공개 배포"로 바뀌면서 다시 씀

## 0. 전제가 바뀌면서 뒤집은 결정 — `server.url`

**바꿨다. `app/capacitor.config.ts`에서 뺐다.**

처음에는 앱이 GitHub Pages 주소를 그대로 띄우게 만들었다. 웹만 배포하면 앱도 같이
갱신돼서 APK를 다시 뿌릴 일이 거의 없다는 게 컸다. 지인 배포에서는 옳은 선택이었다.

스토어에서는 **리젝 사유**다.

| 규정 | 내용 |
| --- | --- |
| Apple 4.2 (Minimum Functionality) | 웹사이트를 그대로 감싼 앱은 리젝된다. "웹에서 못 하는 일"이 있어야 한다 |
| Apple 2.5.2 | 심사를 통과한 뒤 기능이 바뀌는 구조를 금지한다. `server.url`이 정확히 그것이다 |
| Play (최소 기능성) | 같은 취지의 정책이 있다 |

### 이 결정이 낳는 결과 두 가지

**1. 화면을 고칠 때마다 심사를 받아야 한다.** 웹 배포만으로 앱이 갱신되던 이점은 사라졌다.
오타 하나를 고쳐도 새 빌드를 올려야 한다(Play는 보통 몇 시간, Apple은 하루 이틀).

**2. 갤러리 자동 스캔이 "있으면 좋은 기능"에서 "없으면 리젝되는 기능"이 됐다.**
Apple 4.2를 통과하려면 웹으로는 불가능한 네이티브 기능이 있어야 하는데, 지금 계획 중인
것 가운데 그 역할을 할 수 있는 건 갤러리 자동 스캔뿐이다. 우선순위를 다시 봐야 한다.

개발 중에는 매번 새로 까는 게 낭비라, 환경변수를 준 빌드에서만 예전처럼 원격 주소를
띄우게 열어뒀다. **배포용 빌드에는 절대 들어가면 안 된다** — 워크플로는 이 값을 주지 않는다.

```bash
# 개발용(빠른 확인). 이 APK는 나눠주지 않는다
MOACON_DEV_SERVER=https://ceaser501.github.io/our-home-gift/ npx cap sync android
```

## 1. iOS: Sign in with Apple이 필수다

**[App Store 심사 지침 4.8](https://developer.apple.com/app-store/review/guidelines/)** —
구글·카카오·네이버 같은 제3자 로그인을 제공하는 앱은, 아래 세 조건을 모두 만족하는
**대등한 로그인 수단을 함께 제공해야 한다.**

1. 수집 정보를 이름과 이메일로 제한
2. **이메일 주소를 감출 수 있게 할 것**
3. 광고 목적으로 앱 사용 기록을 수집하지 않을 것

지금 있는 이메일 매직 링크는 2번을 만족하지 못한다(실제 이메일을 그대로 받는다).
그래서 **Sign in with Apple을 새로 붙여야 한다.** 안 붙이면 iOS 심사를 통과할 수 없다.

- Supabase는 Apple 제공자를 기본 지원한다. Apple Developer 계정에서 Service ID와 키를 만들어 넣는다.
- 안드로이드에도 버튼이 보여도 되지만, 필수인 건 iOS다.
- 애플이 돌려주는 이메일이 릴레이 주소(`...@privaterelay.appleid.com`)일 수 있다.
  **계정을 이메일로 식별하는 지금 구조에서는**, 같은 사람이 다른 수단으로 로그인하면
  다른 계정이 된다(`client/src/auth.js`에 이미 적힌 문제와 같다). 이 부분은 별도 설계가 필요하다.

## 2. Play: 사진 접근 권한이 심사 대상이다

갤러리 자동 스캔은 `READ_MEDIA_IMAGES`(광범위한 사진 접근)를 쓴다. 이건
**[Play의 사진·동영상 권한 정책](https://support.google.com/googleplay/android-developer/answer/14115180)**
대상이다.

- 이 권한을 유지하려면 Play Console에서 **선언 양식을 제출하고 심사를 통과**해야 한다.
- "핵심 기능이 지속적·빈번한 사진 접근을 필요로 한다"를 입증해야 한다.
- 통과하지 못하면 권한을 빼야 하고, **그러면 자동 스캔 기능 자체가 불가능해진다**
  (대안인 사진 선택 도구(Photo Picker)로는 사용자가 고른 사진만 볼 수 있어서,
  "알아서 훑는다"가 성립하지 않는다).

**이건 실재하는 리스크다.** 기능을 다 만든 뒤 심사에서 막힐 수 있다. 그래서 순서를 이렇게 잡는다:

1. 자동 스캔 없이도 앱이 성립하게 만든다(수동 등록 + 공유로 등록이 이미 그 역할을 한다)
2. 자동 스캔은 **꺼져 있어도 앱이 멀쩡한** 선택 기능으로 붙인다
3. 선언이 반려되면 그 기능만 빼고 출시한다

0번에서 적었듯 Apple 4.2를 위해서는 네이티브 기능이 필요한데, Play에서 반려되면
안드로이드는 그 기능 없이 나가게 된다. 두 스토어의 요구가 반대로 걸리는 지점이라
**iOS용 네이티브 기능을 하나 더 확보해두는 편이 안전하다**(예: 위젯, 바코드 스캐너,
공유 익스텐션).

## 3. 딥링크를 App Links / Universal Links로 올려야 한다

지금 로그인 복귀에 쓰는 `io.github.ceaser501.moacon://login`은 **커스텀 스킴**이다.
다른 앱이 같은 스킴을 등록하면 로그인 결과를 가로챌 여지가 있다. 지인 배포에서는 감수할
만했지만, 공개 배포에서는 그대로 두면 안 된다.

제대로 하려면 **도메인 소유 증명**이 필요하다.

- Android: `https://<도메인>/.well-known/assetlinks.json`
- iOS: `https://<도메인>/.well-known/apple-app-site-association`

`ceaser501.github.io/our-home-gift/`는 루트에 파일을 올릴 수 없어서 지금은 불가능하다.
두 가지 길이 있다:

1. **`ceaser501.github.io` 라는 이름의 저장소를 따로 만들어 루트를 확보한다.** 공짜다.
   주소가 GitHub 사용자명에 묶이지만, 소유 증명 파일을 올리는 데는 아무 문제가 없다.
2. **도메인을 산다** (연 1.5~2만원, 매년 갱신). 스토어 등록 정보에 적기 좋고 사용자명에
   묶이지 않는다. 다만 **필수는 아니다** — 자세한 건 아래 6-2장.

## 4. Play는 APK가 아니라 AAB를 받는다

지금 `.github/workflows/build-android-apk.yml`은 APK를 만든다. Play에 올리려면
**AAB(Android App Bundle)**가 필요하다(`./gradlew bundleRelease`).

APK도 계속 쓸모가 있다 — 심사 전 지인 테스트용. 워크플로가 둘 다 만들게 바꾸면 된다.

Play에 올리면 **앱 서명 키를 구글이 관리**(Play App Signing)하게 되는데, 이때 지금 만든
키는 "업로드 키"가 된다. 지금 키를 그대로 쓸 수 있으니 새로 만들 필요는 없다.

## 5. iOS 빌드 파이프라인이 새로 필요하다

- Apple Developer Program: **연 $99**
- 빌드에 macOS가 필요하다. GitHub Actions의 `macos-latest` 러너로 자동화할 수 있다.
- 인증서·프로비저닝 프로파일을 시크릿으로 관리해야 한다(안드로이드 키스토어와 같은 방식).
- `Info.plist`에 권한 목적 문자열을 넣어야 한다. **한국어로, 왜 필요한지 구체적으로.**
  두루뭉술하면 그것만으로 리젝된다.
  - `NSPhotoLibraryUsageDescription` — 기프티콘 이미지를 등록하기 위해
  - `NSLocationWhenInUseUsageDescription` — 주변 사용처를 찾기 위해
  - `NSCameraUsageDescription` — 기프티콘을 촬영해 등록하기 위해 (쓰는 경우)

### 안드로이드에만 있어서 같이 옮겨야 하는 것 — 설정 열기

권한을 거절한 사람에게 **[설정 열기]** 버튼을 보여주는 자리가 두 곳 있다.
`client/src/components/NearbyStoresSheet.jsx`(위치)와
`client/src/components/GalleryScanSheet.jsx`(사진)다.

지금은 안드로이드에서만 뜬다. `client/src/utils/gallery.js:442`의 `canOpenAppSettings()`가
`isGalleryScanSupported()`를 그대로 쓰고 있어서다 — 그건 **안드로이드 네이티브**일 때만
참이다. 실제로 여는 코드도 자바 한 곳에만 있다
(`app/android/app/src/main/java/io/github/ceaser501/moacon/GalleryPlugin.java`의
`openAppSettings`, `Settings.ACTION_APPLICATION_DETAILS_SETTINGS`).

- [ ] 스위프트 쪽에 같은 이름의 메서드를 만든다 — `UIApplication.openSettingsURLString`
- [ ] `canOpenAppSettings()`를 사진첩 훑기와 떼어내고 `android`·`ios` 둘 다 통과시킨다.
      **지금 하나로 묶여 있는 것이 사고 지점이다.** 사진첩 훑기는 아이폰에서 못 하는 일이고,
      설정 열기는 되는 일인데 같은 판정을 쓰고 있다
- [ ] 아이폰 실기에서 거절 → [설정 열기] → 그 앱 권한 목록으로 바로 가는지

아이폰 쪽이 오히려 낫다. 안드로이드는 앱 정보 화면까지만 가서 권한을 한 번 더 눌러 들어가야
하는데, 아이폰은 그 앱의 권한 목록에 바로 떨어진다.

공장 자동화 회사라 가족용 기프티콘 앱을 찾아볼 일이 없다.

대신 **퇴로를 열어뒀다.** 앱 식별자를 이름에서 떼어 `io.github.ceaser501.ourhomegift`로
바꿨다(예전 값은 `io.github.ceaser501.moacon`).

식별자는 **스토어에 한 번 올리면 절대 못 바꾼다.** 바꾸면 같은 앱이 아니라 새 앱이 되고,
깔아둔 사람들은 갱신을 못 받는다. 게다가 스토어 주소에 그대로 노출된다
(`play.google.com/store/apps/details?id=...`). 여기에 moacon을 박아두면, 나중에 이름을
바꿔도 그 글자는 영영 남는다.

이제 이름을 바꿔야 할 일이 생기면 **화면에 뜨는 글자 한 줄만 갈고 업데이트를 내면 된다.**
사용자는 다시 깔 필요가 없다.

바꾼 자리: `app/capacitor.config.ts`, `app/android/app/build.gradle`(namespace·applicationId),
안드로이드 자바 패키지 폴더, `app/android/…/res/values/strings.xml`,
`app/ios/App/App.xcodeproj/project.pbxproj`.

**딥링크 스킴(`io.github.ceaser501.moacon://login`)은 일부러 그대로 뒀다.** 같은 값이
세 곳에 적혀 있어서다 — 앱, Supabase Redirect URLs, 네이버 Edge Function 시크릿
`NAVER_ALLOWED_REDIRECTS`. 셋을 동시에 바꾸지 않으면 그사이 로그인이 깨진다. 그리고
이 값은 화면에 안 보이고 스토어에도 안 나가며 앱을 새로 내면 언제든 바꿀 수 있다.
못 바꾸는 것은 applicationId 하나뿐이라, 그것만 지금 처리했다.

앱 이름은 올라간 뒤에 바꾸면 그때까지 쌓인 검색·리뷰·링크가 함께 흔들린다.
**아직 아무것도 안 올라간 지금이 바꾸기 제일 싼 때다.**

(개발자 이름은 유일해야 하는 값이 아니고 나중에 바꿀 수 있다. 앱 이름과는 사정이 다르다.)

### 그 밖에

- **"기프티콘"은 상표로 등록된 이력이 있는 단어다.** 일반명사처럼 쓰이지만, 앱 이름이나
  스토어 등록 정보에 쓰는 것과 일상 대화에서 쓰는 것은 다르다. 출시 전에
  [특허정보넷 키프리스](http://www.kipris.or.kr)에서 확인해두는 편이 좋다.
- **다른 회사의 브랜드명·로고**가 앱 화면이나 스크린샷에 들어가면 문제가 될 수 있다.
  실제 브랜드가 들어 있던 목데이터는 걷어냈지만, 스토어 스크린샷을 찍을 때 화면에 뜬
  기프티콘의 상호는 그대로 사진에 남는다. 찍기 전에 한 번 본다.
- 앱이 기프티콘을 **거래·중개**하지 않는다는 점은 분명히 해두는 게 좋다. 금융·상품권
  관련 규제와 스토어 정책 양쪽에서 민감한 영역이다.

## 6-2. 돈이 얼마나 드나 — 등록비보다 운영비가 무섭다

### 도메인은 필수가 아니다

앞에서 "도메인을 권한다"고 적었는데, **없어도 출시할 수 있다**는 점을 분명히 해둔다.
스토어가 요구하는 건 개인정보처리방침 URL과 지원 URL인데, 둘 다 지금의 GitHub Pages
주소로 충분하다. App Links도 `ceaser501.github.io` 라는 이름의 저장소를 따로 만들면
루트(`/.well-known/`)를 확보할 수 있어서 공짜로 된다.

도메인을 사면 얻는 건 스토어 등록 정보의 신뢰감과 GitHub 사용자명에 묶이지 않는 주소다.
**있으면 좋고, 없다고 막히지 않는다.** 그리고 **도메인은 영구 구매가 아니라 매년 갱신**이다
(`.com` 기준 연 1.5~2만원, 첫 해 특가에 속지 말고 갱신가를 볼 것). 갱신을 놓치면 남이
가져가고, 그러면 App Links 소유 증명이 깨져서 로그인이 망가진다. 자동 갱신을 켜둔다.

### 고정비

| 항목 | 비용 | 주기 |
| --- | --- | --- |
| Google Play Console | $25 (약 3.5만원) | **평생 1회** |
| Apple Developer Program | $99 (약 14만원) | **매년** — 안 내면 앱이 스토어에서 내려간다 |
| 도메인 (선택) | 1.5~2만원 | 매년 |

### 사용량 비례 — 여기가 진짜다

이미지 인식은 `claude-haiku-4-5`를 쓴다($1 / 100만 입력 토큰, $5 / 100만 출력 토큰).
기프티콘 한 건은 축소본 이미지 1장(약 1,200토큰) + 프롬프트 + JSON 응답 정도라
**등록 1건당 대략 4~5원**이다(2장 올리면 7원 안팎).

| 규모 | 월 등록 건수 | 인식 비용 |
| --- | --- | --- |
| 100명 | 1,000건 | 약 4,000원 |
| 1,000명 | 10,000건 | 약 4만원 |
| 10,000명 | 100,000건 | 약 40만원 |

가격 검색은 웹 검색을 쓰기 때문에 **1회당 20~40원**으로 훨씬 비싸다. 자주 눌리는 버튼이
아니라 지금은 괜찮지만, 사용자가 늘면 여기부터 조인다.

> 자동 스캔 쪽은 [scan-cost.md](scan-cost.md)에 따로 정리해뒀다 — 어느 갈래에서 돈이 나가고
> (찾기는 공짜, 정보 읽기만 과금), 세는 단위가 사진 장수가 아니라 기프티콘 건수라는 것,
> 줄일 수 있는 자리가 어디인지.

### ⚠️ 스토리지가 먼저 터진다

`client/src/api.js:54`의 `uploadImages()`는 **사용자가 고른 파일을 그대로 올린다.**
분석용으로는 긴 변 1400px로 줄인 사본을 쓰면서(`client/src/utils/imageAnalyze.js`),
보관은 원본으로 한다. 요즘 폰 캡처는 한 장에 1~2MB라, 기프티콘 한 건이
**원본 + 바코드 크롭 + 썸네일 ≈ 1.5MB** 를 차지한다.

- Supabase 무료 티어(스토리지 1GB) 기준 **약 700건이면 찬다.**
- 스토리지는 누적된다. 지우지 않는 한 줄지 않는다.
- 목록을 열 때마다 썸네일을 내려받으므로 **대역폭도 같이 늘어난다.**

**고치는 방법은 이미 코드 안에 있다.** 분석용으로 만드는 축소본(1400px JPEG)을 보관용으로도
쓰면 한 건이 1.5MB에서 150KB 안팎으로 줄어든다 — **10분의 1**이다. 원본 화질이 필요한
기능은 없다(바코드는 이미 크롭해서 따로 저장하고, 목록은 썸네일을 쓴다).

### 남이 우리 예산을 태우는 건 이미 막혀 있다

돈이 나가는 함수 앞에는 `supabase/functions/_shared/guard.ts`가 문지기로 붙어 있다.
`requireUser`가 진짜 로그인 사용자인지 auth 서버에 직접 물어보고(anon key로는 통과 못 한다),
`withinDailyLimit`가 사용자별·전체 일일 호출 수를 센다. `analyze-gifticon`, `search-price`,
`search-places` 등 종량 요금이 붙는 함수가 모두 이 문을 지난다.

[docs/security.md](security.md)의 조치 현황표에는 2번이 아직 "대기"로 적혀 있지만
**코드에는 이미 들어가 있다.** 남은 건 배포와 설정 확인이다.

- [ ] `supabase functions deploy`로 최신 코드가 올라가 있는지
- [ ] `ALLOWED_ORIGINS` 시크릿 설정 (비워두면 모든 출처를 허용한다)
- [ ] 일일 상한값이 규모에 맞는지 (`limitFromEnv`가 읽는 환경변수)
- [ ] **Anthropic 콘솔의 월 사용량 상한과 알림** — 최후의 방어선. 코드에 구멍이 나도
      금액이 여기서 갇힌다. 5분이면 되고 미룰 이유가 없다.

둘은 서로를 안 기다린다. 같은 날 신청한다.

#### 둘 다 개인으로 낸다 (2026-09-02 정함)

위 14일을 피하려면 법인 계정이어야 한다. 가족 중에 부동산 개인사업자가 있어서 그 사업자
등록증을 쓰는 길을 따져봤고, 쓰지 않기로 했다. 세 가지 때문이다.

**애플이 애초에 안 받는다.** 애플은 법인만 조직으로 인정한다. D-U-N-S 기록에
sole proprietorship으로 잡히면 "법인으로 확인되지 않음"으로 거절하고 개인으로 가입하라고
안내한다. 개인사업자는 여기서 걸린다. 그러면 아이폰은 어차피 개인 계정이 되고, 두 스토어의
개발자명이 갈린다.

**구글은 되지만 더 느리다.** 조직 계정은 D-U-N-S가 필요한데 발급에 최대 30일이 걸린다.
피하려던 14일보다 오래 걸린다.

**계정이 그 사업자의 것이 된다.** 구글은 조직 계정에 사업자등록증과 **대표자 본인**의 신분
확인을 요구한다. 즉 계약 주체·개발자명·세금·분쟁 통보가 전부 그 사업으로 간다. 스토어에는
부동산 사무소 이름이 개발자로 뜨고, 나중에 빼려면 앱 이전 절차를 밟아야 한다.

그래서 개인으로 낸다. 14일은 손해가 아니다 — 그 2주 동안 Sign in with Apple(3단계)을
해야 하고, 그게 남은 것 중 제일 크다. 나란히 흐른다.

무료 앱을 개인으로 내는 데 사업자등록은 필요 없다. 두 스토어 개인 계정은 사업자등록증을
묻지 않는다. 나중에 사업자를 내면 그때 조직으로 옮길 수 있다.

- [애플 — Program enrollment](https://developer.apple.com/help/account/membership/program-enrollment/)
- [Google Play 개발자 인증: 대한민국 필수 서류](https://support.google.com/googleplay/android-developer/answer/15633622?hl=ko&co=GENIE.CountryCode%3DKR)

## 출시 확정 뒤에 몰아서 할 것 (2026-08-21 정함)

**지금 손대지 않는다.** iOS·안드로이드 기능 검토를 다 끝내고, 스토어에 내겠다고
확정한 다음에 한꺼번에 한다. 순서를 이렇게 잡은 이유는 셋 다 되돌리기가 번거롭고,
기능이 아직 움직이는 동안 하면 매번 다시 손봐야 해서다.

### 1. AI 호출 한도를 견적 기준으로 낮춘다

지금은 1인 하루 30 / 전체 하루 500이다. 처음 견적을 낼 때의 기준으로 되돌린다.

| | 지금 | 바꿀 값 |
| --- | --- | --- |
| 1인 하루 | 30 | **10** |
| 전체 하루 | 500 | **200** |
| 전체 한 달 | (없음) | **6,000** |

앞의 둘은 Supabase 시크릿만 바꾸면 된다 — 배포가 필요 없다.

```
supabase secrets set ANALYZE_DAILY_LIMIT=10 ANALYZE_TOTAL_DAILY_LIMIT=200
```

**한 달 한도는 지금 없다.** `bump_api_usage`와 `api_usage_total`이 날짜별로만 세고 있어서,
달 단위로 세는 자리를 새로 만들어야 한다(SQL + guard.ts).

**1인 하루 10이 부족할 수 있다는 것은 적어둔다.** 자동스캔은 찾은 기프티콘마다 한 번씩
부르므로, 사진첩에 15개가 있으면 첫 스캔에서 15건이 나간다. 수동 등록도 여섯 장을 고르면
여섯 건이다. 예전에 같은 이유로 1인 한도를 50까지 올렸다가 30으로 내린 적이 있다
(guard 주석에 남아 있다). 낮출 때 처음 쓰는 사람의 첫날을 같이 봐야 한다 —
"처음 며칠은 넉넉히" 같은 예외를 두든, 10으로 두고 막히는 화면 문구를 손보든.

### 2. 저장소를 private으로 돌린다

보안 때문이 아니다. RLS·스토리지·Edge Function 인증은 이미 걸려 있고, Supabase anon key는
원래 공개되는 값이다(앱 안에도 들어 있다). 자산 관리 때문이다.

막히는 것은 하나다 — **무료 계정은 private 저장소에서 GitHub Pages를 못 쓴다.**
스토어에 올라간 뒤에는 웹이 정책·소개 페이지로 줄어들므로, 그때 Cloudflare Pages로
옮기면서 닫는다(private 무료 지원, 커스텀 도메인 무료).

개인정보처리방침은 **공개 URL이어야 한다** — 두 스토어 모두 심사 항목이다. 이 페이지만은
어떤 경우에도 공개로 남는다.

### 3. 아이폰은 앱으로 낸다

웹으로 대신하지 않는다. `npx cap add ios`는 해뒀다 — `app/ios/`에 Xcode 프로젝트가 있고,
아이콘·진입 화면·권한 문구·로그인 복귀 스킴까지 맞춰져 있다. 남은 것은 FCM 토큰을 주는
플러그인으로 교체하는 일이고(`@capacitor/push-notifications`는 iOS에서 APNs 토큰을 준다 —
서버는 FCM 토큰을 기다린다), 그 앞단에 애플 개발자 계정($99/년)이 있다.

빌드는 **맥북에서 Xcode로 직접** 한다. GitHub Actions의 맥 러너는 분을 10배로 차감해서
private 무료 한도(월 2,000분)로는 월 15번쯤밖에 못 돈다. 안드로이드는 지금처럼 CI로 둔다.
맥이 없을 때 컴파일만 확인하는 용도로 `.github/workflows/build-ios-app.yml`을 손으로
돌릴 수 있다(설치 파일은 안 나온다 — 서명할 계정이 없어서다).

자세한 것은 `docs/ios-release.md`.
